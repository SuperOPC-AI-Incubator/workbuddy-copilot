# 开营前的学员网络实测

学员机上的连接器只访问本应用自己的域名，但**浏览器和 MCP 客户端会直连 Supabase 项目主机**。后者是受限网络下最先坏掉的部分，所以必须单独验证，而且要在**学员真实使用的网络**里验证，不是在办公室或开着代理的开发机上。

Supabase 项目在 `ap-southeast-1`（新加坡），主机在 Cloudflare 上，国内不同运营商、不同时段的表现差异很大。**一次成功不能证明开营那天可用**，请在不同时段各跑一次。

## 第一步：自动探测（必要条件）

```sh
sh scripts/ops/check-student-network.sh
```

可调环境变量：`APP_ORIGIN`（默认生产域名）、`ATTEMPTS`（默认 3）、`TIMEOUT`（默认 20 秒）。

脚本不需要任何凭证，也不硬编码 Supabase 主机——它从应用发布的 `/.well-known/oauth-protected-resource` 里读出当前项目，所以迁移项目后仍然测的是对的目标。

五条探测分别对应的真实后果：

| 探测                          | 期望                              | 红了意味着                                 |
| ----------------------------- | --------------------------------- | ------------------------------------------ |
| 应用站点                      | 200                               | 网页和连接器全不可用                       |
| MCP protected-resource 元数据 | 200                               | 应用异常，且无法判断该测哪个 Supabase 项目 |
| Supabase Auth (HTTPS)         | 任意 HTTP 响应（无 key 时为 401） | **学员注册和登录直接卡死**                 |
| Supabase Realtime (WebSocket) | 任意 HTTP 响应（无 key 时为 401） | 导师消息不会自动出现，要手动刷新才看到     |
| 连接器 ingest（POST）         | 恰好 401                          | 学员对话传不上来，导师台没有数据           |

两点关于判读的说明：

- **401 是通的意思。** 这些端点在没有 API key 时按设计就返回 401，能收到 401 说明 TLS 和 HTTP 链路是开的。真正的坏是**超时**（脚本记为 `http=000`）。
- ingest 那条要求**恰好 401**，因为这个应用对未授权的 GET 会返回单页应用的 HTML；用 GET 探会拿到 200，看着是绿的其实根本没碰到路由。脚本因此用 POST 探。

`FLAKY`（部分成功）要当失败处理：开营当天的间歇性不可用同样是事故。

## 第二步：人工验证（充分条件）

自动探测只能证明网络路径开着，**不能**证明注册流程、WebSocket 升级和消息送达真的成功。以下三件必须在学员机的浏览器/客户端里真做一遍：

1. **注册。** 用学员网络打开 `/auth`，注册一个测试账号。这一步浏览器是**直连 Supabase Auth** 的（`supabase.auth.signUp`），是整条链路上唯一没有服务端兜底的环节。注册后应立刻拿到会话并进入工作台（生产环境关闭了邮箱确认）。
2. **导师消息实时到达。** 学员保持页面打开，导师端发一条消息，**不刷新**看它是否自己出现。出现即 Realtime WebSocket 正常；必须刷新才看到，说明退化成了定时轮询——功能不算坏，但导师会误判学员没收到。
3. **连接器同步一轮。** 在学员机上跑一次 WorkBuddy 同步，确认导师台出现这一轮对话。这条走的是本应用域名，通常最稳。

测完删掉测试账号，或记录下来后续清理，别把测试数据留在导师台里。

## 已知缺口：MCP 客户端的 OAuth 发现是断的

如果计划让学员用 **MCP 客户端**（而不是连接器）接入，注意这个尚未解决的问题：

- 应用发布的 `/.well-known/oauth-protected-resource` 把 Supabase 项目声明为授权服务器（已验证返回 200，指向 `https://<project-ref>.supabase.co/auth/v1`）。
- 但该 issuer 的 `/.well-known/oauth-authorization-server` 返回 `404 feature_disabled`：`"OAuth server is disabled"`。
- 本应用自己也没有提供这份授权服务器元数据（同路径返回单页应用兜底）。

结论：**按标准做 OAuth 发现的 MCP 客户端会走到死路**，因为它找不到 `/authorize`、`/token` 和动态客户端注册。资源服务器一侧的 JWT 校验（走 JWKS）不受影响，所以如果客户端能通过别的途径拿到 Supabase access token，工具调用仍然可用。

连接器路径不受此影响——它用的是 `issue_workbuddy_credential` 签发的 bearer token，完全不经过 OAuth。

在决定是否把 MCP 作为学员接入方式之前，请先用**真实 MCP 客户端**验证这条流程，不要依据"`/mcp` 返回 401 挑战"就认为它可用。
