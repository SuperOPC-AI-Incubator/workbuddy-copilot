# 导师账号管理

团队管理员可在 `/admin/mentors` 创建、停用、启用导师账号，以及重置临时密码。只有同时满足以下条件的账号能够调用管理服务：

- 账号已启用；
- 已完成首次密码修改；
- 拥有 `team_admin` 角色。

页面是否显示入口不构成授权依据。每个服务端操作都会重新检查调用者状态，账号状态写入还会由仅限 `service_role` 的数据库函数再次检查。创建账号时，Supabase Auth 身份创建完成后，常规数据库入口会在自己的事务里再次确认创建者仍然是已启用、已完成首次改密的团队管理员；调用者在两步之间被停用或失去权限时，创建会失败并清理刚创建的 Auth 身份。

Supabase Auth 的管理员建号流程可能在首次插入用户后才写入受信任的 app metadata。前向迁移因此也会识别版本化内部导师邮箱的精确格式，在触发器阶段避免把导师临时建成学员。该格式只用于阻止学员数据落账，不授予任何导师角色；即使公开注册者伪造同格式邮箱，也只会得到没有角色和资料的不可用账号。

该前向迁移不会自动删除升级前已经产生的“双身份”测试账号。当前无数据环境必须先应用迁移，再初始化导师；若复用曾经用旧流程创建过导师的 Supabase 项目，应重建无数据项目，或在核对具体账号后单独清理，不能用宽泛迁移删除学员数据。

## 首次初始化

首次账号通过 `scripts/bootstrap-mentors.ts` 初始化。用户名和管理员用户名可以作为非敏感命令行参数提供；密码只能从交互式 TTY 读取并以掩码显示，不能通过命令行、环境变量或文件传入。

```sh
bun scripts/bootstrap-mentors.ts \
  --usernames-json '["mentor.example","admin.example"]' \
  --admin-username 'admin.example'
```

脚本会逐个提示输入临时密码。重新运行时，已经存在的用户名会被跳过，现有密码不会被重置。初始化完成后，导师首次登录必须立即修改密码。

首次初始化使用独立的 `bootstrap_staff_account` 数据库入口。该入口只授予 `service_role`，不接受普通管理员身份，也不会用空的 `created_by` 冒充常规创建；日常创建必须走需要明确创建者的 `provision_staff_account`。

Auth Admin 更新密码后，原刷新令牌会失效。首次改密服务会先更新密码、完成数据库门禁，再用新密码签发与同一 `userId` 绑定的替代会话；浏览器只接受这组新会话令牌后才进入工作台。替代会话失败时不会回退旧令牌，用户可使用新密码重新登录。

## 状态安全

- 停用和启用共用带版本号、操作令牌的同步状态。开始操作时数据库先进入停用状态，再把当前目标状态同步到 Supabase Auth；只有版本和令牌仍匹配时，数据库才会确认最终状态。
- 两个状态操作交错时，较旧请求会读取并协助收敛到最新目标状态，再返回“状态已被更新”。较旧确认无法覆盖较新的停用或启用；启用确认失败时会尝试恢复 Auth 封禁，数据库仍保持停用。
- 重置临时密码时先设置 `must_change_password=true`，并记录本次重置的唯一操作令牌和原值。Auth 更新失败时，只有仍持有该令牌的请求可以恢复原标志；旧请求不能清除较新重置留下的改密门禁。
- 停用、创建和开始重置密码这些会影响管理员可用性的操作共用一把事务锁，并在获得锁后重新验证调用者。重置另一个可用团队管理员前还会确认至少仍有一名可用团队管理员，因此两个管理员相互重置，或一方开始重置后另一方尝试停用对方，都不能把系统变成无可用管理员的状态。
- 团队管理员不能从账号管理页重置自己的临时密码；当前账号应使用正常的修改密码流程。
- 管理员不能停用自己，也不能使系统失去最后一个可用且已完成改密的团队管理员。

数据库落账失败时，服务会先删除刚创建的 Auth 身份。若删除也失败，会尽力长期封禁残留身份，并记录仅包含事件代码、封禁结果和 Auth `userId` 的结构化运维日志；对应错误详情也只包含封禁结果和 `userId`。

临时密码和内部邮箱不会出现在响应、管理列表、错误详情或应用日志中。
