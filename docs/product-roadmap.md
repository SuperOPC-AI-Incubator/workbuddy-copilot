# WorkBuddy Copilot 产品路线图

> 更新日期：2026-07-24
>
> 状态：云端产品整合后的迭代基线
>
> 优先级原则：先闭合真实链路和稳定性，再提高导师效率，最后扩展适配器与分析能力

## 1. 路线结论

当前产品基线是已经完成本地整合与验证的 TanStack/Supabase 云端产品。团队导师账号、可靠双向链路、跨平台连接器、送达状态、领域包、自动化测试、CI 和腾讯云发布资产均已进入目标集成分支，不再作为后续路线项重复规划。

Python 项目只作为可靠性、学员助教和测试方法的设计供体，不再是产品运行主线。当前目标是把“本地已经闭环”推进为“真实云资源、真实账号、真实设备上稳定闭环”，再进入小规模灰度。

优先级定义：

- **P0 / Now**：不完成就不能认为产品闭环可用。
- **P1 / Next**：闭环稳定后，直接提升导师效率和学员体验。
- **P2 / Later**：需要真实运行数据或明确的新平台需求后再启动。

### 2.2 本地验证状态

- 自动化结果：**353 passed，4 项环境依赖用例 skipped**；
- skip 仅对应需要真实 Supabase、真实部署或真实设备的环境门，不能视为线上通过；
- 本地已验证 build、类型、核心协议、浏览器流程、连接器和发布资产；
- Python 项目的 spool、Student Core、五层上下文、诊断包和闭环测试经验已被选择性吸收为设计与验收方法，不再单独计算为当前产品交付状态。

### 2.3 尚未完成

剩余工作集中在真实环境，而非继续补本地基础能力：

- 创建或确认团队真实 Supabase 项目并执行 migrations；
- 实际初始化管理员、导师与测试学员账号；
- 在腾讯云真实部署、配置域名与 HTTPS，并验证回滚；
- 使用真实 Windows WorkBuddy 设备验证自动同步；
- 在真实 macOS/Windows、真实 Supabase、真实腾讯云之间完成全链路验收；
- 完成 2–3 台学员机灰度；
- 将现有实时告警升级为可认领、可解决的持久注意力队列。

## 3. Now：先完成真实闭环与稳定性

### P0-1 创建团队 Supabase 并初始化真实账号

目标：把本地 schema、RLS、RPC 和账号管理能力落到团队控制的真实项目。

验收标准：

- 团队明确 Supabase owner、协作者、区域、账单与备份责任；
- 全部 migrations 在新项目一次执行成功，重复检查不产生漂移；
- 初始化管理员、至少一名导师和两名测试学员；
- 导师可使用确定性用户名登录，管理员可创建、停用和重置导师；
- 使用真实 Supabase 运行环境用例，4 项环境 skip 中相关项目转为通过；
- 不在提交、日志或测试报告中写入实际密钥。

### P0-2 完成腾讯云真实部署

目标：使用已经验证的发布资产建立可访问、可观察、可回滚的线上环境。

验收标准：

- Node/Nitro 服务、Nginx、域名和 HTTPS 正常；
- `/api/health`、`/api/ready`、MCP metadata 和未认证 ingest 拒绝均符合预期；
- 应用只从部署环境读取 Supabase、AI 和账号管理凭据；
- Realtime 或 DeepSeek 不可用时，基础同步、导师查看和人工回复仍可工作；
- 发布失败可切回上一 release，数据库变更保持向前兼容；
- 使用真实部署环境运行 smoke test，相关环境 skip 转为通过。

### P0-3 完成真实设备全链路验收

目标：证明本地自动化覆盖的双向协议在真实 WorkBuddy 和真实网络上成立。

验收标准：

- macOS 与 Windows 各至少一台真实学员机完成接入；
- 连续多轮对话经 MCP 或连接器进入正确会话；
- 重复发送同一事件只入库一次，并发会话不串线；
- 学员离线时导师发送两条消息，恢复后 WorkBuddy 依序呈现并 ACK；
- 导师网页分别显示 `web_seen` 与 WorkBuddy `acknowledged`；
- 人为断网、重启应用和重复 ACK 后无消息丢失或重复展示；
- 真实 Windows 设备门通过后，才宣称 Windows 自动同步可用。

### P0-4 完成 2–3 台灰度

目标：用一个完整学习时段验证产品在真实使用中的稳定性与支持成本。

验收标准：

- 灰度覆盖至少两种接入方式或两个操作系统；
- 记录同步成功率、补传次数、可见时延、导师消息确认率和失败原因；
- 导师能在同一工作台识别在线、漏传、待补传和未送达状态；
- AI 故障不阻断人工导师闭环；
- 灰度问题有负责人、复现信息和处理结果，不采集额外原文；
- 达到团队约定的稳定性门后再扩大范围。

### P0-5 建立持久导师注意力队列

目标：把现有 SOS、warn、error、漏传和失败提醒从即时通知升级为多人可协作处理的队列。

验收标准：

- 告警持久化、去重，并可认领、稍后处理和解决；
- 记录处理导师与时间，多导师看到一致状态；
- 每条告警可跳转到具体学员、会话和证据；
- 浏览器通知、声音和标题闪烁只是可关闭的加速层；
- warn 有节流，SOS/error 不被后续普通事件覆盖；
- 断开 Realtime 后重新连接，队列无缺口、无重复。

## 4. Next：提升导师效率与学员助教体验

### P1-1 增强 AI 导师草稿

把当前“基于最近时间线起草”升级为使用当前会话、学习分析、脱敏诊断摘要和有效 guidance 版本。

验收标准：

- 必须由导师主动触发，草稿只进入输入框，绝不自动发送；
- 上下文严格限定当前学员和会话；
- UI 标明本次使用的上下文类别；
- LLM 失败不影响导师手工发送；
- 保存“采用、编辑后采用、放弃”的匿名产品指标，用于判断真实价值。

### P1-2 深化学员技术助教

以 Python 项目的设计经验为参考，把五层上下文、诊断包、能力状态和明确空状态带入当前 TanStack/Supabase 产品，不迁移旧运行时。

验收标准：

- 学员可选择同步后提问或明确不带会话提问；
- 诊断默认有界、脱敏、可取消，服务端记录实际是否使用；
- LLM 状态区分 ready、配置缺失、超时和上游错误；
- 回答可复制，服务不可用不伪装成“暂无分析”；
- 任一学员的上下文不得混入其他学员或其他会话。

### P1-3 Guidance 与领域包管理

在已经实现的通用/工业自动化 domain pack 基础上，提供最小的预览、发布和回滚入口。

验收标准：

- 默认提供通用 AI 学习营包，工业自动化 PLC 作为可选包；
- 每次分析和问答记录实际使用版本；
- 发布前可用固定样例预览，空版本或坏版本不能直接生效；
- 新版本只影响后续请求，历史结果保持可解释；
- 回滚不要求重启客户端或重写历史数据。

### P1-4 优化导师协作与运营反馈

根据灰度数据补充告警分派、处理时限、重复问题聚合和接入自检，不在没有真实数据前预设复杂工作流。

验收标准：

- 注意力队列可按状态、严重度、学员和处理导师筛选；
- 重复问题能聚合但仍可回到原始会话；
- 接入页可显示最近成功同步、队列积压和可执行自检；
- 关键失败有稳定错误码和面向学员/导师的不同说明；
- 新增规则由灰度问题驱动，并有采用率或故障下降证据。

## 5. Later：由真实数据触发扩展

### P2-1 可选原生 Student Core 适配器

只有当真实灰度证明 Skill/MCP 的漏传、延迟或宿主限制无法接受时，才将当前 Hook/EventSpool/Student Core 封装为云端产品的可选可靠采集器。启动条件是有量化的失败率和明确的平台需求，不因“代码已经存在”而提前移植。

### P2-2 群体学习与干预效果分析

在身份、采集完整度和导师处理记录稳定后，再分析 capture coverage、响应时长、重复卡点和干预后续。每个指标必须同时展示缺失数据，不把描述性数据解释为因果，不在本阶段引入学员排名。

### P2-3 托管架构再评估

只有当托管 Supabase 的成本、所有权、访问质量或合规要求成为真实问题时，再评估完整迁移或自建。当前先按已完成的 Node/Nitro + 托管 Supabase 方案上线，不为“自主可控”提前扩大运维面。

## 6. 明确暂缓与不做

为服从原型期“功能闭环优先”的决定，以下事项不作为当前发布阻塞项：

- 注册时角色自选的权限加固；
- public ingest 的 session 归属安全校验；
- 全面隐私合规、字段级加密和复杂审计后台；
- Redis/MQ、死信队列、多区域或多活；
- 两个无共同祖先仓库的直接 Git 合并；
- 在闭环数据可信前开发大屏或复杂分析。

这表示接受原型期风险，不表示问题不存在。只有用户重新提高安全或正式发布要求后，才进入独立设计与测试。

## 7. 主要风险与控制

| 风险 | 影响 | 当前控制 |
|---|---|---|
| Skill/MCP 依赖模型按要求调用 | 漏传或延迟 | event_id、失败可见、原子补传队列、真实成功率统计 |
| Realtime 被误当作可靠送达 | 导师误判学员已收到 | 独立 delivery 状态、拉取与呈现后 ACK |
| 会话使用标题或时间窗合并 | 对话串线 | source session key、冲突测试、并发会话负控 |
| Windows 只有网页证据 | 自动同步无法交付 | 真实 Windows WorkBuddy 验收；无设备则保持未验证 |
| 告警过多 | 导师注意力被反向占用 | 分级、去重、节流、认领与解决状态 |
| AI 服务故障 | 草稿/诊断不可用 | 同步和人工导师链路独立降级 |
| 云资产归属不清 | 无法发布、备份或回滚 | P0-1/P0-2 完成 owner、账单、备份和密钥责任交接 |
| 本地验证被误当作线上通过 | 过早扩大灰度 | 本文固定区分“本地已验证 / 真实环境已验证 / 尚未完成” |

## 8. 阶段退出门

### Now → Next

必须同时满足：

1. 团队真实 Supabase 已创建、迁移完成，管理员/导师/测试学员实际可登录；
2. 腾讯云正式环境、域名、HTTPS、健康检查和回滚实测通过；
3. macOS 与 Windows 真实 WorkBuddy 双向链路通过；
4. 正向重复事件不重复入库，离线导师消息恢复后呈现并确认；
5. 2–3 台灰度完成，核心指标和失败记录可查询；
6. 持久注意力队列可供多导师认领与解决；
7. 353 条本地测试保持通过，4 项环境 skip 中与已具备环境相关的项目转为通过。

### Next → Later

必须同时满足：

1. 导师注意力队列和 AI 草稿在真实使用中有明确采用率；
2. 学员助教上下文与诊断无跨学员、跨会话污染；
3. guidance/domain pack 可追溯和回滚；
4. 已积累足够的稳定运行数据，能够区分产品问题与数据缺失。
