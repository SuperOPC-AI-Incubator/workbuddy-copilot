# WorkBuddy Copilot 产品路线图

> 更新日期：2026-07-24
>
> 状态：云端产品整合后的迭代基线
>
> 优先级原则：先闭合真实链路和稳定性，再提高导师效率，最后扩展适配器与分析能力

## 1. 路线结论

产品后续以同事版云端原型为候选产品主线，保留其双角色网页、Realtime、WorkBuddy 接入、告警和 AI 导师草稿体验；当前 Python 项目作为可靠性与学员助教能力供体，逐步移植幂等、补传、诊断、真实送达和闭环测试能力。

两个代码库没有共同 Git 历史，不做源码硬合并，也不在本阶段重新讨论技术栈。当前目标是把“能演示的云端原型”推进为“可以稳定完成学员—AI—导师双向闭环的产品”。

优先级定义：

- **P0 / Now**：不完成就不能认为产品闭环可用。
- **P1 / Next**：闭环稳定后，直接提升导师效率和学员体验。
- **P2 / Later**：需要真实运行数据或明确的新平台需求后再启动。

## 2. 当前基线与整合状态

### 2.1 当前项目已验证

以下能力已经在当前 Python 主线落地，并有自动化或真机记录：

- stdlib-only Hook、本地原子 spool、Student Core、失败补传与断线恢复；
- 完整 transcript、会话隔离、上传与诊断双轴状态；
- 学员技术助教：当前会话跟随、五层上下文、结构化脱敏诊断、LLM 能力状态；
- 导师消息先落库、离线补拉、学员呈现后 REST 回执，避免把 WebSocket 写成功误判为送达；
- 导师三栏观察台、完整原文、同步状态、诊断失败重试；
- 598 条自动测试通过记录；macOS 主链路已有真机验证，Windows 仍缺 W0/W1 真实证据。

这些能力是后续云端整合的质量基线，不要求照搬 Python/FastAPI/SQLite 实现。

### 2.2 同事云端原型已运行

以下能力已存在于同事版 TanStack/Supabase 原型，可保留产品交互：

| 能力 | 当前判断 | 后续处理 |
|---|---|---|
| 学员/导师双角色网页 | 已运行 | 保留为主要产品界面 |
| Supabase Auth、RLS、Realtime | 已运行 | 原型期保留托管形态 |
| 三栏导师观察台 | 已运行 | 保留并补真实送达状态 |
| SOS / warn / error 告警 | 已运行 | 保留，后续补持久化与处理状态 |
| 浏览器通知、声音、漏传提示 | 已运行 | 保留为加速层，不作为唯一告警记录 |
| AI 导师草稿 | 已运行 | 保留“人工确认、不自动发送” |
| WorkBuddy 一键 Skill 接入 | 已运行 | 保留降级入口，补可靠队列与多平台说明 |
| OAuth MCP 工具面 | 已运行 | 作为首选接入候选，必须经过真实 WorkBuddy 验收 |
| 学员网页时间线与呼叫导师 | 已运行 | 保留并补连接、失败、送达状态 |

### 2.3 已纳入整合设计，但尚未实现

以下内容已经进入[云端整合设计](superpowers/specs/2026-07-23-superbrain-cloud-integration-design.md)和[实施计划](superpowers/plans/2026-07-23-superbrain-cloud-integration.md)，不能写成已交付：

- `event_id` 幂等写入、稳定 source session key、冲突检测；
- 导师消息 `pending → fetched → acknowledged` 持久状态；
- MCP 未读消息拉取与确认工具；
- Token 接口、Windows/macOS 连接器、本地原子待发送队列；
- 网页已看与 WorkBuddy 已送达分离；
- 通用 AI 学习营与工业自动化 domain pack；
- Vitest、Playwright、多系统 CI、腾讯云发布与回滚。

## 3. Now：先完成真实闭环与稳定性

### P0-1 建立云端主线质量基线

目标：让每次改动都有可重复的最低门，结束“能 build 但不可验证”的原型状态。

验收标准：

- format、lint、typecheck、unit/integration test、production build 均有固定命令且返回 0；
- ingest、导师消息、账号和 UI 关键路径均先有能见红的负控；
- 测试断言具体内容、状态和事件 ID，不只断言 HTTP 200 或结果非空；
- CI 不读取真实用户目录，不访问真实外网，不输出 token、密码或完整 transcript；
- 当前已知 lint/typecheck 基线问题归零，不把 warning 当成功。

复用：沿用当前项目“真 Store/数据库 + 确定性假 LLM + 防假绿”的测试纪律；不复制 Python 测试实现。

### P0-2 闭合学员到导师的正向链路

目标：每一轮 WorkBuddy 对话可稳定、可重试、可定位地进入正确会话。

验收标准：

- 每轮包含稳定 `event_id`、source session key、来源和客户端时间；
- 相同事件重试只写一次；相同 ID 携带不同内容返回冲突；
- 并发会话不按“同标题”或“最近 6 小时”静默合并；
- MCP 为首选时，失败有明确反馈；Token/连接器失败先落项目目录外的原子队列并可补传；
- 导师网页能实时看到新事件；Realtime 不可用时退化为有界刷新；
- Windows 与 macOS 的接入说明、配置生成和队列逻辑进入 CI。

复用：保留同事版 `log_turn` 和一键接入体验；移植当前项目的幂等、补传、会话隔离和失败可见语义。

### P0-3 闭合导师到 WorkBuddy 的反向链路

目标：导师发出的消息不仅出现在网页数据库中，还能在学员 WorkBuddy 内呈现并形成真实回执。

验收标准：

- 导师发送后先持久化为 `pending`，学员离线不丢；
- MCP/Token 客户端可按稳定 cursor 拉取未读消息，重复拉取不重复展示；
- 学员端呈现成功后才确认 `acknowledged`；
- 网页 `web_seen` 与 WorkBuddy `acknowledged` 分开显示；
- 服务重启、网络中断、重复 ACK 后状态仍正确；
- 导师端明确显示待送达、已拉取、WorkBuddy 已送达或失败原因。

复用：保留同事版导师 compose 和 Realtime 展示；移植当前项目“先落库、呈现后确认、离线补拉”的送达协议。

### P0-4 完成跨平台接入与真实双端验收

目标：证明网页跨平台之外，WorkBuddy 自动同步在真实学员机上也成立。

验收标准：

- 接入页分别提供 MCP、Windows PowerShell、macOS/Linux 三种明确入口；
- token 不写进仓库、日志或可复制的 Skill 正文；连接器只从受限配置读取；
- 至少一台 macOS 和一台 Windows 学员机完成连续多轮同步；
- 人为制造断网、重复上传、并发会话和离线导师消息，恢复后无丢失、无串线、无重复展示；
- 导师端可看到最后成功同步时间、待补传数量和未送达消息数；
- 如果暂时拿不到 Windows 真机，状态必须写“待真机验证”，不能用 CI 代替。

复用：同事版接入页面和 MCP 工具分类；当前项目 Student Core 的队列、重连和回执经验。

### P0-5 完成团队接管、部署与小规模灰度

目标：产品资产、运行环境和回滚路径由团队掌控，并用真实用户验证闭环。

验收标准：

- Lovable、Supabase、GitHub、域名和运行时账号的 owner、协作者、账单与备份责任明确；
- 腾讯云采用独立 release、HTTPS、健康/就绪探针和可回滚部署；
- DeepSeek 不可用时，同步、导师查看和人工回复仍可工作；
- 2–3 台真实学员机完成不少于一个完整学习时段的灰度；
- 灰度记录同步成功率、补传次数、端到端可见时延、导师消息确认率和失败原因，不采集额外原文；
- 灰度通过后再扩大范围，不用“页面能打开”代替闭环验收。

## 4. Next：提升导师效率与学员助教体验

### P1-1 导师注意力收件箱

把 SOS、严重诊断、重复失败、上传/分析失败和漏传统一进入可处理队列。

验收标准：

- 告警持久化、去重，可认领、稍后处理和解决；
- 记录处理导师与时间，多导师看到一致状态；
- 每条告警可跳转到具体学员、会话和证据；
- 浏览器通知与声音可关闭，关闭后不影响站内队列；
- warn 有节流，SOS/error 不被后续普通事件覆盖。

复用：同事版告警、通知、标题闪烁和漏传 UX；不复用仅保存在浏览器内存的临时告警列表。

### P1-2 增强 AI 导师草稿

把当前“基于最近时间线起草”升级为使用当前会话、学习分析、脱敏诊断摘要和有效 guidance 版本。

验收标准：

- 必须由导师主动触发，草稿只进入输入框，绝不自动发送；
- 上下文严格限定当前学员和会话；
- UI 标明本次使用的上下文类别；
- LLM 失败不影响导师手工发送；
- 保存“采用、编辑后采用、放弃”的匿名产品指标，用于判断真实价值。

### P1-3 迁移当前项目的深度学员助教

把五层上下文、诊断包、能力状态和明确空状态带入云端学员体验。

验收标准：

- 学员可选择同步后提问或明确不带会话提问；
- 诊断默认有界、脱敏、可取消，服务端记录实际是否使用；
- LLM 状态区分 ready、配置缺失、超时和上游错误；
- 回答可复制，服务不可用不伪装成“暂无分析”；
- 任一学员的上下文不得混入其他学员或其他会话。

### P1-4 Guidance 与领域包管理

把固定工业自动化提示词改为可替换 domain pack，并提供最小的预览、发布和回滚入口。

验收标准：

- 默认提供通用 AI 学习营包，工业自动化 PLC 作为可选包；
- 每次分析和问答记录实际使用版本；
- 发布前可用固定样例预览，空版本或坏版本不能直接生效；
- 新版本只影响后续请求，历史结果保持可解释；
- 回滚不要求重启客户端或重写历史数据。

## 5. Later：由真实数据触发扩展

### P2-1 可选原生 Student Core 适配器

只有当真实灰度证明 Skill/MCP 的漏传、延迟或宿主限制无法接受时，才将当前 Hook/EventSpool/Student Core 封装为云端产品的可选可靠采集器。启动条件是有量化的失败率和明确的平台需求，不因“代码已经存在”而提前移植。

### P2-2 群体学习与干预效果分析

在身份、采集完整度和导师处理记录稳定后，再分析 capture coverage、响应时长、重复卡点和干预后续。每个指标必须同时展示缺失数据，不把描述性数据解释为因果，不在本阶段引入学员排名。

### P2-3 托管架构再评估

只有当 Lovable/Supabase 的成本、所有权、访问质量或合规要求成为真实问题时，再评估完整迁移或自建。当前腾讯云优先承载 Node/Nitro 应用层，不在 4 GB 共享服务器上为了“自主可控”提前自建整套 Supabase。

## 6. 明确暂缓与不做

为服从原型期“功能闭环优先”的决定，以下事项不作为当前发布阻塞项：

- 注册时角色自选的权限加固；
- public ingest 的 session 归属安全校验；
- 全面隐私合规、字段级加密和复杂审计后台；
- Redis/MQ、死信队列、多区域或多活；
- 两个无共同祖先仓库的直接 Git 合并；
- 在闭环数据可信前开发大屏或复杂分析。

这表示接受原型期风险，不表示问题不存在。只有用户重新提高安全或正式发布要求后，才进入独立设计与测试。

## 7. 主要风险与控制

| 风险 | 影响 | 当前控制 |
|---|---|---|
| Skill/MCP 依赖模型按要求调用 | 漏传或延迟 | event_id、失败可见、原子补传队列、真实成功率统计 |
| Realtime 被误当作可靠送达 | 导师误判学员已收到 | 独立 delivery 状态、拉取与呈现后 ACK |
| 会话使用标题或时间窗合并 | 对话串线 | source session key、冲突测试、并发会话负控 |
| Windows 只有网页证据 | 自动同步无法交付 | 真实 Windows WorkBuddy 验收；无设备则保持未验证 |
| 告警过多 | 导师注意力被反向占用 | 分级、去重、节流、认领与解决状态 |
| AI 服务故障 | 草稿/诊断不可用 | 同步和人工导师链路独立降级 |
| 云资产归属不清 | 无法发布、备份或回滚 | P0-5 前完成 owner、账单、备份和密钥责任交接 |
| 计划状态与实现状态混淆 | 误判已交付 | 本文固定使用“已验证 / 已运行 / 已纳入待实现”三种状态 |

## 8. 阶段退出门

### Now → Next

必须同时满足：

1. 云端主线质量门稳定通过；
2. 正向事件重复发送不重复入库；
3. 学员离线时导师消息不丢，恢复后 WorkBuddy 呈现并确认；
4. macOS 真机通过；Windows 在目标范围内则真机通过，否则明确未验证；
5. 2–3 台灰度完成，核心指标和失败记录可查询；
6. 应用可回滚，AI 故障不影响人工闭环。

### Next → Later

必须同时满足：

1. 导师收件箱和 AI 草稿在真实使用中有明确采用率；
2. 学员助教上下文与诊断无跨学员、跨会话污染；
3. guidance/domain pack 可追溯和回滚；
4. 已积累足够的稳定运行数据，能够区分产品问题与数据缺失。
